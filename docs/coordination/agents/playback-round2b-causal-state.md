## Finding

**[verified]** Frozen v1 is sufficient for a defensible human-facing system explanation if the display keeps two different state spaces separate:

1. **resource allocation/execution state** — exact resource-unit partition;
2. **causal work state** — task/dependency explanations derived from the DAG and event trace.

A single legacy-style HPC partition

`Working + Blocked + Idle + Released = classical capacity`

cannot be derived without ambiguity because `Blocked` is not a resource-allocation state in v1.

## Proposed explanation schema

This is a presentation/explanation schema only. It does not change engine semantics.

```ts
interface SystemStateSnapshot {
  simTimeS: number;

  resources: {
    classicalByPool: Record<string, {
      activeUnits: number;          // exact ResourceInterval(active)
      allocatedIdleUnits: number;   // exact ResourceInterval(allocated-idle)
      releasedUnits: number;        // exact ResourceInterval(released)
      queuedTaskIds: string[];      // exact TaskInterval(queued)
    }>;

    qpuByPool: Record<string, {
      activeUnits: number;          // exact ResourceInterval(active)
      queuedTaskIds: string[];      // exact TaskInterval(queued)
      queueDepth: number;           // exact latest QueueSample at t
    }>;
  };

  causal: {
    activeCommunications: Array<{
      dependencyId: string;
      sourceTaskId: string;
      targetTaskId: string;
    }>;

    policyHeldQuantumTasks: Array<{
      taskId: string;
      resourcePoolId: string;
      qpuDemandUnits: number;
      reason: "maxInFlightQuantumByPool";
    }>;

    dependencyGatedClassical: Array<{
      taskId: string;
      classicalDemandUnits: number; // task demand, NOT allocated/blocked units
      incomingDependencyCount: number;
      unresolved: Array<{
        dependencyId: string;
        sourceTaskId: string;
        directState:
          | "communication-active"
          | "qpu-predecessor-incomplete"
          | "upstream-incomplete";
      }>;
      structuralJoin: boolean;      // graph fact only; does not imply "global"
    }>;
  };
}
```

### Deterministic derivation rules

**[verified] Resource partition**
- At `t`, sum half-open `ResourceInterval [startS,endS)` by pool/state.
- For each classical pool, `active + allocated-idle + released = modeled capacity` in the A-D fixtures.
- Never move an `allocated-idle` or `released` unit into a causal waiting category.

**[verified] Queue state**
- Task identity comes from half-open `TaskInterval.state = queued`.
- Queue depth is the most recent engine-provided `QueueSample` at or before `t`.

**[verified] Active communication**
- A dependency is communication-active after `communication_started` and before matching `communication_completed`.
- Zero-cost control edges create no communication state.

**[verified] Policy-held quantum work**
- A QPU task is policy-held when it occupies a `ready` interval at `t` and has a preceding/current `task_throttled` event for `maxInFlightQuantumByPool`.
- This gives exact **task identity/count and QPU demand units**.
- It does not identify an HPC rank or classical resource unit.

**[verified] Dependency-gated classical continuation**
- From `WorkflowSpec.dependencies`, identify classical tasks that have not reached `task_ready` because one or more incoming dependencies are unresolved.
- Direct unresolved edges can be classified as communication-active, incomplete QPU predecessor, or other upstream dependency.
- For human playback, prefer the immediate causal frontier rather than summing every downstream future classical task.

**[verified] Structural join**
- `incomingDependencyCount > 1` is an exact graph property.
- It proves a multi-input join, not that the join is globally synchronized across ranks.

### Scenario A — local overlap

| t | Classical resource state | QPU | Communication | Policy-held | Immediate classical gate |
|---|---|---|---|---|---|
| 2.0 | active **1**, allocated-idle 0, released **1** | active **1**, queue 0 | none | none | `local-consumer` demand 1; direct QPU predecessor `quantum-run` incomplete |
| 5.5 | active **2**, allocated-idle 0, released 0 | active 0, queue 0 | none | none | none |

**[verified counterexample]** At t=2 CPU capacity is 2 and is already exactly partitioned as 1 active + 1 released. The downstream classical task has demand 1 and is QPU-gated. ## Answers to Agent F's five questions

### 1. Can a top-level Working / Blocked / Idle / Released HPC view be derived without ambiguity?

**No, not as a mutually exclusive classical resource-unit partition.**

**[verified]**
- Working = exact active classical resource units.
- Idle = exact `allocated-idle` only when a fixed reservation exists.
- Released = exact released units.
- Blocked is not a resource interval state.

**[verified]** A, B, C and D all provide concrete double-counting counterexamples if dependency-gated task demand is converted directly into blocked resource units.

A defensible top-level view is therefore:

`Resource state: Working / Allocated-idle / Released`

plus separate causal overlays:

`Dependency-gated / Communication-active / Policy-held / Resource-queued`.

### 2. Can Blocked causes be separated into own QPU result / communication / global synchronization?

**Partially, at task/dependency level; not as exact rank-level blocked counts.**

**[verified]**
- **Communication:** yes. An active positive-duration dependency edge is explicit.
- **QPU predecessor:** yes. A classical continuation can be shown as gated by an incomplete QPU predecessor.
- **Multi-input join:** yes. Incoming dependency fan-in is explicit.

**[uncertain without authored provenance]**
- **"own QPU result":** v1 has no persistent actor/rank identity proving that a downstream classical task belongs to the same rank that submitted a QPU task. Use "QPU-gated local continuation" unless metadata states stronger semantics.
- **"global synchronization":** graph fan-in proves a join, not that it is globally collective. Scenario B is known to be collective from the accepted preset contract, but a generic user-authored DAG with the same shape need not be global.

### 3. Can Scenario-D policy-held work be converted into an HPC-rank/resource-unit count?

**No.**

**[verified]** v1 proves the held QPU task identities, their QPU `resourceCount`, throttle reason, and admission-wait duration. It does not preserve a classical rank/resource owner across CPU→QPU→CPU stages.

A UI may say:
- `4 quantum tasks policy-held`;
- `4 QPU-demand units held` if their QPU resource counts sum to 4.

It may not say:
- `4 HPC ranks idle by throttling`.

### 5. Smallest additional provenance needed

**Recommendation: no engine event/state extension for Round 2B.**

The generic explanation layer is deterministic from `WorkflowSpec + SimulationResult` if it avoids rank-level blocked counts.

If the product needs stronger human labels, use existing `TaskSpec.metadata` rather than changing DES behavior. The smallest useful authored annotation is approximately:

```ts
metadata: {
  continuationKind?: "local-result" | "collective-join";
}
```

Then:
- a single QPU predecessor + `local-result` can be labeled "local QPU-result wait";
- a multi-input join + `collective-join` can be labeled "collective synchronization wait";
- communication remains derived from explicit dependency events.

If the requirement is specifically **exact rank-level Blocked counts** or "this CPU rank owns this QPU request", one metadata label is insufficient. That would require a persistent actor/allocation-affinity model across stages, which is a substantive IR/engine extension and is outside frozen v1.

## Recommendation

# **DERIVE**

Build a presentation/explanation layer over frozen `WorkflowSpec + SimulationResult`.

Do **not** extend engine v1 merely to recreate the historical Working/Blocked/Idle counter.

The product should expose:
1. an exact resource-state partition;
2. causal task/dependency overlays;
3. optional authored semantic metadata for local-vs-collective wording.

This preserves technical correctness and still supports the visual-debugger goal.
