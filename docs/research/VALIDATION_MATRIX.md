# Agent E Validation Matrix — Quantum–HPC Workflow Explorer

Date: 2026-10-02  
Role: Agent E — Research / Validation  
Scope: implementation-relevant evidence only

## Decision summary

The first serious reference case should be the IBM/QAMP Fe4S4 SQD C/C++/MPI/OpenMP workflow, modeled as a **structural preset**, not as a calibrated performance predictor.

The engine baseline should remain deterministic and small:

- DAG dependencies define execution order;
- resource capacities constrain runnable tasks;
- communication dependencies use an affine latency/bandwidth baseline;
- queue/resource/task state remain distinct;
- provider queue delay is not invented from a constant;
- published queueing relations are validation aids, not a substitute simulator.

The legacy A–D animations remain useful only as optional stress/regression concepts after their state counts are generated by the authoritative engine.

| Claim | Evidence status | Implementation consequence |

| Current IBM fair-share scheduling dynamically interleaves workloads from instances; completion order is not generally guaranteed from submission order, and exact execution time cannot generally be guaranteed. | **[verified]** IBM fair-share scheduler documentation. | Do not turn “provider queue time” into a fixed deterministic production prediction. |
| IBM job/batch wall-clock “in progress” time can include classical preprocessing and QPU contention; that wall time is not equivalent to QPU usage. | **[verified]** IBM monitoring documentation. | Queue/wall time must not automatically be charged as QPU active resource time or cost. |

### Queue terminology for the Explorer

Use three different concepts:

1. **resource queue** — tasks admitted to a modeled resource pool but waiting for capacity;
2. **policy wait** — ready tasks withheld by a local admission-control rule such as `maxInFlightQuantum`;
3. **external/provider wait** — remote scheduler delay, only included when the user supplies an explicit assumption/model.

**[opinion]** The serious IBM preset should default external/provider wait to zero/omitted and state “provider wait excluded.” A separate illustrative stress preset may add an explicitly synthetic external delay.

## 3. Analytical communication baseline

### Affine latency/bandwidth model

**[verified]** A standard simple message model is the Hockney/alpha-beta form:

[
T_{comm}(M) = \alpha + \beta M
]

where (alpha) is fixed latency, (eta) is inverse bandwidth, and (M) is message size. Equivalently:

[
T_{comm} = latency + \frac{bytes}{bandwidth}
]

The provisional `DependencySpec` fields `fixedLatencyS`, `dataBytes`, and `bandwidthBytesPerS` map directly to this baseline.

**Known limitation [verified]:** this simple expression does not model network contention or computation/communication overlap.

**[opinion]** For the 10-day product, keep this baseline rather than adding LogP/LogGP/contention models. A communication dependency delays its consumer by the computed transfer cost, while independent tasks may still execute concurrently.

**[opinion]** `communicationSeconds` should mean summed modeled transfer exposure, not “critical-path penalty.” Concurrent transfers can make those two quantities differ.

## 4. Queueing literature: use as sanity checks, not engine semantics

**[verified]** Little's Law relates long-run average number in a stable system (L), throughput/arrival rate (lambda), and average time in system (W):

[
L = \lambda W
]

This is useful as a consistency check for sufficiently long, stationary-style test traces.

**[opinion]** Do not require exact Little's-Law equality for arbitrary finite transient runs. Do not introduce an M/M/c stochastic simulator merely to make this relation available.

**[opinion]** Saturation/capacity fixtures should instead have exact deterministic expected starts, waits, and makespans. The engine can later expose stochastic service models only if the product actually needs them.

## 5. Slurm/resource-allocation semantics relevant to the model

**[verified]** Slurm allocates resources to a job for a duration and then launches job steps within that allocation. Allocation may be exclusive or shared depending on configuration/options.

**[verified]** Slurm documentation explicitly notes that exclusive node allocation can leave allocated resources unused by the job.

**[opinion]** Therefore the Explorer's distinction between `active`, `allocated-idle`, and `released` is technically useful.

**[important interface gap]** The provisional v0 contract has task-level `resourceCount` and policy `allocation: "fixed" | "release-aware"`, but no explicit amount/scope of a fixed workflow reservation. That is insufficient to represent a batch job that reserves N MPI-rank slots while only rank 0 is active during the quantum stage.

Requested clarification/change for Agent A/F:

- define how a workflow-level fixed reservation size is represented;
- or add an equivalent explicit reservation field/object;
- ensure task active usage can be smaller than reserved allocation;
- ensure resource accounting can distinguish active vs allocated-idle units.

Affected producers/consumers: engine model, metrics, UI resource timeline, comparison view.

Migration impact: v0 mocks need one explicit reservation assumption; no legacy production API exists yet.

Acceptance case: the scaled IBM topology fixture in section 8.

## 6. Serious preset: IBM/QAMP Fe4S4 SQD structural workflow

### Preset identity

Suggested id: `ibm-sqd-fe4s4-reference`  
Suggested label: **IBM/QAMP Fe4S4 SQD — compiled HPC reference**

Purpose: explain the actual hybrid structure behind the QAMP project and provide a non-toy reference DAG.

It is a **reference topology**, not a benchmark and not a prediction of IBM queue/runtime performance.

### Structural DAG

```text
MPI job/allocation established
        |
        v
rank 0: load/setup
        |
        v
rank 0: build LUCJ circuit
        |
        v
rank 0: transpile circuit
        |
        v
rank 0 -> QPU: sample once; wait for result
        |
        v
for recovery iteration k = 0..N-1:
    rank 0: configuration recovery
        |
    rank 0: subsample / prepare SBD input
        |
    all MPI ranks: SBD diagonalization
        |
    occupancy update / next recovery iteration
        |
        +---- bounded repeat ----+
```

### Resource assumptions

- CPU/HPC pool: configurable; IBM README example uses 96 MPI ranks, but this is not universal.
- QPU pool: capacity 1 for the current IBM Quantum Compute reference preset only.
- GPU: none required by this reference.
- Network: communication can be represented through dependencies if the product wants visible transfer cost; no production transfer values are supplied by the sources.
- Fixed allocation: useful to represent the MPI job remaining allocated while only rank 0 performs/awaits the quantum segment.
- Provider queue: excluded by default.
- Monetary cost: excluded by default.

### Service times

**[uncertain]** The public sources do not provide a general production-calibrated set of per-stage service times that would make this preset predictive across systems.

**[opinion]** Any numeric times shipped for demo/playback must be tagged **illustrative synthetic values** and kept separate from the structural claims.

## 8. Engine acceptance cases

These are deterministic **synthetic fixtures**. They are not measured QPU/HPC performance.

### E1 — QPU capacity must be configurable

Five independent QPU tasks are ready at t=0. Each service time = 2 s.

Expected:

| QPU capacity | Start times (s) | Makespan (s) | Sum queue wait (s) |
|---:|---|---:|---:|
| 1 | 0, 2, 4, 6, 8 | 10 | 20 |
| 2 | 0, 0, 2, 2, 4 | 6 | 8 |
| 5 | 0, 0, 0, 0, 0 | 2 | 0 |

For capacity 2, active QPU resource-seconds = 10 and utilization over [0,6] is 10/(2*6) = 5/6.

Validates: resource capacity, queue wait, configurable QPU capacity, deterministic ordering/tie rule.

### E2 — Communication dependency baseline

- task A: CPU, 1 s
- dependency A -> B:
  - fixedLatencyS = 0.5
  - dataBytes = 1000
  - bandwidthBytesPerS = 1000
- task B: CPU, 1 s

Expected transfer cost = 0.5 + 1000/1000 = 1.5 s.  
B cannot start before t=2.5 s.  
Makespan = 3.5 s.  
communicationSeconds = 1.5 s.

Validates: dependency safety + affine communication baseline.

### E3 — Fork/join represents barrier-like dependency

- root: 1 s
- three independent branches after root: 2 s, 4 s, 6 s
- enough CPU capacity for all branches to overlap
- join task: 1 s, depends on all three branches

Expected: root ends t=1; branches finish t=3,5,7; join starts t=7; makespan=8 s.

Validates: DAG semantics and global “all required” synchronization without a separate barrier state machine.

### E4 — Bounded in-flight quantum work

- six independent QPU tasks ready t=0
- QPU capacity=1
- service time=2 s each
- maxInFlightQuantum=2

Requested semantics:

- “in flight” = admitted but not complete, including running + resource-queued;
- at most two tasks can be in flight;
- with capacity 1, maximum modeled QPU resource queue depth is therefore 1;
- remaining ready tasks are in **policy wait**, not the QPU queue;
- makespan remains 12 s in this no-overhead fixture.

Validates: policy wait vs resource queue separation.

### E5 — Scaled IBM fixed-allocation topology

Synthetic scaled topology:

- CPU allocation capacity/reservation: 4 abstract MPI-rank slots
- QPU capacity: 1
- strict structural sequence:
  - rank0 load: 1 s, CPU 1
  - rank0 build: 2 s, CPU 1
  - rank0 transpile: 2 s, CPU 1
  - quantum sample/result wait: 4 s, QPU 1; CPU active usage 0 during wait
  - recovery 0: 1 s, CPU 1
  - SBD 0: 3 s, CPU 4
  - rank0 occupancy bookkeeping: 0.5 s, CPU 1
  - recovery 1: 1 s, CPU 1
  - SBD 1: 3 s, CPU 4
  - rank0 occupancy bookkeeping: 0.5 s, CPU 1

Expected makespan = 18 s.  
Expected QPU active resource-seconds = 4.  
Expected CPU active resource-seconds = 32.

If a fixed policy reserves all 4 CPU units for the full 18 s:

- allocated CPU resource-seconds = 72;
- allocated-idle CPU resource-seconds = 40.

If a release-aware comparison is idealized with zero reacquisition delay/contention:

- allocated CPU resource-seconds = 32;
- allocated-idle CPU resource-seconds = 0;
- makespan remains 18 s.

This comparison validates accounting semantics. It does **not** claim that a real Slurm job can dynamically release/reacquire MPI ranks this way.

### E6 — External/provider queue must be explicit

Take any single QPU task with service time 2 s.

Base preset: external provider wait omitted -> makespan contribution from modeled QPU service = 2 s.

Illustrative variant: user supplies external provider delay 5 s -> task cannot start QPU service before t=5; makespan contribution = 7 s.

Acceptance requirement: the assumptions list must identify the 5 s value as user/synthetic external delay. It must not be inferred from “IBM queue” or billed as 7 QPU-active seconds.

## 9. Interface clarifications requested from Agent A/F

### R1 — Fixed reservation size

Current limitation: `allocation: "fixed"` has no explicit reserved quantity/scope.

Proposed semantic capability: represent a workflow/job reservation separately from instantaneous task active usage.

Affected consumers: engine resource intervals/metrics; UI timeline; compare mode.

Acceptance: E5.

### R2 — `maxInFlightQuantum` definition

Current limitation: “in flight” is undefined.

Proposed definition: admitted quantum tasks that are not complete = running + queued for QPU capacity. Tasks held back by admission control remain policy-waiting and must not inflate the QPU queue depth.

Affected consumers: engine queue accounting; playback labels; UI queue chart.

Acceptance: E4.

### R3 — External/provider delay

Current limitation: v0 has resource queue series but no explicit distinction for externally supplied provider delay.

**[opinion]** Do not add a full provider-scheduler model. Either:
- represent external delay as an explicitly labeled dependency/task assumption, or
- defer it from v1 and keep serious presets provider-wait-free.

Affected consumers: engine assumptions/trace; UI labels.

Acceptance: E6.

### Scope relative to the Explorer

**[opinion]** This model belongs in the Explorer as an **analytical diagnostic/baseline**, not as authoritative execution semantics.

The discrete-event engine should remain authoritative for:

- dependency ordering;
- overlapping tasks;
- resource capacity and contention;
- policy wait vs resource queue;
- allocated-idle vs released resources;
- nonuniform repeated subgraphs;
- makespan and trajectory-derived metrics.

The Rao equations are useful for:

- a fast “communication importance” diagnostic from explicit user/preset inputs;
- cross-checking a simple homogeneous cycle;
- explaining when latency/bandwidth changes are capable of mattering;
- comparing an event-simulated workflow against a coarse cycle-average approximation.

**[opinion]** The engine should not infer (C_C), (C_Q), (F), (V), (L), or (B) from unrelated fields. Any displayed (R_{cc}) must be trace-derived from a deliberately defined cycle or computed from explicit analytical inputs with assumptions shown.
